# Plan: Add BusyBox Across Ready Architectures

## Summary

Add BusyBox 1.38.0 as a statically linked multi-call recovery utility for
`aarch64`, `armv7`, `x86`, and `x86_64`. Pin one reviewed configuration and
runtime applet inventory per architecture, distribute only the `busybox`
executable, and land all four ready-architecture artifacts atomically.

## Problem

The repository distributes focused diagnostic binaries but lacks a compact
general-purpose toolbox for constrained or damaged systems. BusyBox fills that
gap, but its behavior is determined by hundreds of Kconfig choices. Merely
building upstream `defconfig` would leave the committed feature contract
implicit and vulnerable to accidental drift.

BusyBox also carries GPLv2-only source obligations and applets whose useful
behavior depends on kernel facilities or external runtime data. The recipe
therefore needs an exact configuration, a runtime-visible applet inventory,
representative multi-call tests, and candid documentation that the artifact is
not a root filesystem or a symlink installation.

## Scope

In scope:

- Add BusyBox 1.38.0 as `artifacts/<architecture>/busybox` for every ready
  architecture.
- Start from upstream `defconfig`, review and commit the complete resolved
  `.config`, enable a fully static build, and record the exact expected applet
  list for each architecture.
- Retain the broad upstream applet profile, including shell, file, text,
  process, archive, checksum, and networking applets, while making any required
  static-musl omissions explicit.
- Test exact applet membership plus representative shell, file, text, archive,
  checksum, and link behavior on each target architecture.
- Preserve and document all license notices needed for the selected source and
  built-in components.

Out of scope:

- Installing an applet symlink farm, constructing an initramfs/root filesystem,
  publishing a container image, or changing host `/bin` links.
- Treating `busybox nc` or `busybox netstat` as the standalone artifacts planned
  separately for those names.
- Adding downstream applets, shell aliases, configuration files, CA bundles,
  timezone/locale data, terminfo, user databases, device nodes, or kernel
  modules.
- Curating a tiny bespoke applet subset or promising GNU-compatible behavior
  for every option.
- Builder changes, generic configuration tooling, root README changes, or a new
  artifact-policy mechanism.

## Design

Use the official HTTPS `busybox-1.38.0.tar.bz2` release archive with accepted
SHA-256
`34f9ea6ff8636f2c9241153b9114eefa9e65674a45318ae1ef95bb5f31c53bb2`.
Upstream labels 1.38.0 an unstable release; use it deliberately as the latest
published source release and state that status in every recipe README and
`TRUST.md`. Declare `checksum-only`: upstream publishes both a checksum and a
DSA signature, but no signer key backed by authenticated official full-
fingerprint evidence has been adopted. Do not attempt PGP and fall back after
failure.

Generate the initial configuration from 1.38.0 `defconfig`, set
`CONFIG_STATIC=y`, and resolve it with the release's own Kconfig machinery.
Commit the complete resolved file as `busybox.config` in each recipe; normal
builds copy that exact file into the verified source tree and run
`olddefconfig` only as a consistency check, failing if it changes any setting.
Do not write configuration interactively. Use fixed build metadata such as
`SOURCE_DATE_EPOCH`/Kbuild timestamp inputs supported by BusyBox so the binary
does not incorporate the current wall clock, without claiming byte-for-byte
reproducibility before it is demonstrated.

Commit `expected-applets.txt`, generated from and reviewed with the resolved
configuration. The guest build and target smoke test compare sorted
`busybox --list` output exactly to this file, so applet additions and removals
cannot enter through an incidental config or upstream-default change. The
recipe README summarizes the profile by category and points to the exact list
instead of copying hundreds of names into prose.

BusyBox Kconfig makes `CONFIG_PIE` depend on `!CONFIG_STATIC`, so select classic
static `ET_EXEC` for this tool. Build with `CONFIG_STATIC=y`, no explicit
`-no-pie`, `-O2 -pipe`, and a final linker map; add
`-march=i686 -msse2 -mfpmath=sse` for x86. Strip the single multi-call binary
and fail if it does not match the selected ELF profile. If the locked builder
cannot produce this profile, stop rather than weakening static validation or
changing the builder inside this rollout.

Treat BusyBox 1.38.0 as GPL-2.0-only. Retain the complete corresponding source
archive in every recipe and review the upstream `LICENSE` plus notices for
selected bundled implementations. The recipe license inventory distinguishes
source-built BusyBox code from builder-provided musl/libgcc archives and maps
every final linked archive to package/source, version, license text, and source
evidence. Document that keeping the recipe and tracked source with the binary
is how this repository supplies corresponding source; do not claim that a
checksum alone authenticates it.

The smoke test invokes applets as `busybox <applet>`, never through ambient
host symlinks. In addition to exact version and applet-list checks, it runs an
`ash` script that creates files/directories, uses `cp`, `mv`, `ln`, `find`,
`sort`, `grep`, `sed`, and `awk`, verifies a `sha256sum`, and performs a tar
archive round trip while preserving a symbolic link. Use only a temporary
directory, compare exact outputs, and bound cleanup. These operations cover
multi-call dispatch and several shared internal libraries without invoking
privileged or host-destructive applets.

Each architecture recipe follows the existing Buildx candidate-first flow and
consumes only its committed builder digest. The target smoke container has no
external network. Host validation repeats the guest ELF checks, installs only
after success, and requires the installed hash to equal the candidate hash.

## Affected Components

- `recipes/busybox/{aarch64,armv7,x86,x86_64}/`: add Dockerfiles, host/guest
  builds, smoke tests, READMEs, source locks and archives, exact BusyBox config
  files, expected applet lists, and license/link inventories.
- `recipes/catalog.tsv`: add four enabled `busybox` rows.
- `artifacts/{aarch64,armv7,x86,x86_64}/busybox`: add four validated multi-call
  executables.
- `artifacts/SHA256SUMS`: add sorted checksum records for all four artifacts.
- `TRUST.md`: add the four checksum-only source records, upstream's unstable
  release label, and the unavailable authenticated signing-key limitation;
  record no independent artifact evidence unless it is actually produced.

## Implementation Sequence

1. Download 1.38.0 and its published checksum into temporary storage, verify
   the exact accepted bytes, release page, size, GPLv2-only terms, and selected
   bundled notices, then copy identical mode-100644 archives into all four
   recipe directories.
2. On x86-64, derive and review the resolved static `defconfig`, capture the
   exact applet list, implement link/ELF validation and the representative
   smoke test, and run a real locked-builder build before cloning the recipe
   shape.
3. Add AArch64, ARMv7, and x86 recipes with the same config and applet profile;
   change only platform, target/ABI validation, and the explicit x86 baseline.
   Require `olddefconfig` and runtime applet output to remain identical on all
   four architectures.
4. Warn that the remaining Buildx/QEMU builds may exceed ten minutes and give
   a rough estimate. Build and target-test every architecture, retaining only
   candidates that pass the full config, applet, functional, link, and ELF
   checks.
5. Review the four binary sizes before staging, add all catalog rows together,
   update the exact checksum manifest and trust records, and audit the GPL
   source/license path for each distributed binary.
6. Run focused and full repository validation, then commit and push the
   complete BusyBox rollout and completed-plan record without unrelated files.

## Validation

- Run `bash -n` on host scripts, `sh -n` on guest/smoke scripts,
  `git diff --check`, and config-file format/sorted-app-list checks.
- Verify every tracked archive against the accepted SHA-256. Require
  `source.lock` to declare `checksum-only` and the build to print that weaker
  assurance without attempting PGP.
- Run `olddefconfig` non-interactively and compare the resulting `.config`
  byte-for-byte with `busybox.config`; compare sorted target
  `busybox --list` output byte-for-byte with `expected-applets.txt`.
- For every candidate and installed output, require the correct machine, ELF
  class, endianness, ABI, stripped state, classic `ET_EXEC`, no `PT_INTERP`, and
  no `DT_NEEDED`. Require ARMv7 hard-float details and the x86
  i686/CMOV/SSE2 compilation baseline.
- Parse the final linker map and require a complete license/source inventory
  for every static archive, including selected source-bundled code and locked
  builder libraries.
- On all four targets, check exact BusyBox 1.38.0 identification and run the
  applet-list, shell, file/link, text-processing, checksum, and tar round-trip
  tests in a temporary directory with no external network.
- Require installed/candidate hash equality, then run
  `sha256sum -c artifacts/SHA256SUMS` and `./validate.sh`.
- Confirm all four ready architectures are present and no symlink farm,
  rootfs, runtime image, builder, standalone nc/netstat recipe, generic script,
  root README, or architecture policy changed.

## Success Criteria

- `./build.sh busybox <architecture>` rebuilds each artifact from tracked
  1.38.0 source and the exact locked builder on a fresh checkout.
- All four artifacts are stripped static `ET_EXEC` binaries with identical
  reviewed applet membership and successful representative target behavior.
- The exact Kconfig and applet list make feature drift visible and fatal.
- Users are told that this is the upstream-labeled unstable 1.38.0 release, a
  multi-call executable rather than a rootfs/symlink installation, and that
  some applets require external files, kernel support, or privileges.
- GPLv2 corresponding source, bundled notices, linked-input provenance,
  catalog rows, checksums, and trust limitations are complete for every ready
  architecture without introducing unrelated infrastructure.
