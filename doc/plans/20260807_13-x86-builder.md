# Plan: Add the 32-bit x86 Full-Suite Builder Foundation

## Summary

Add `builders/x86/` and publish one immutable Alpine 3.24.1 builder for OCI
platform `linux/386`. Define the target as Alpine's 32-bit x86 ABI: ELF32,
little-endian, i686-compatible, with CMOV and SSE2. Lock the smallest package
union required by the repository's six current utilities so the x86 rollout
uses one reviewed builder release rather than publishing a tcpdump-only image
and immediately replacing it.

Execute this plan after `20260807_12-architecture-onboarding.md` and before
`20260807_14-x86-tcpdump.md` and the remaining x86 recipe plans.

## Problem

The repository has no 32-bit x86 build environment or x86 row in the generic
builder catalog. Ordinary recipes may consume only an already-published builder
digest, so adding an x86 artifact before the builder foundation would advertise
an architecture whose immutable environment does not exist. The earlier
tcpdump-only package scope is also too narrow for the now-required complete
six-tool matrix and would force a wasteful second publication before the other
x86 recipes could build.

Alpine names this port `x86` and defines it as 32-bit i686-compatible with CMOV
and SSE2. Docker and OCI expose the same image as `linux/386`; the pinned Alpine
3.24.1 index currently identifies its `linux/386` child as
`sha256:6f5908cdf811d574b30ec394e405ef74ee293bed5af1620a5187d604604a90a8`.
These different spellings must remain boundary translations rather than leak
into repository paths.

Relevant platform authorities:

- [Alpine's architecture matrix](https://wiki.alpinelinux.org/wiki/Include%3AArchitecture_support_matrix)
  defines the `x86` CPU baseline.
- [Docker's builder documentation](https://docs.docker.com/build/builders/)
  uses `linux/386` as the container platform.
- [The OCI image configuration specification](https://github.com/opencontainers/image-spec/blob/main/config.md)
  derives architecture values from GOARCH, where 32-bit x86 is `386`.
- [The pinned binfmt helper](https://github.com/tonistiigi/binfmt) exposes
  `linux/386` through `qemu-i386` when native execution is unavailable.

## Scope

In scope:

- Create a digest-pinned Alpine 3.24.1 `linux/386` builder under
  `builders/x86/` with the smallest direct package union required by GDB,
  GDBserver, lsof, socat, strace, and tcpdump at their current feature profiles.
- Validate the exact packages, build commands, compiler-owned static archives,
  Alpine package architecture, OCI architecture, and executable static x86
  probes required by those six recipes.
- Add one `x86`, `linux/386`, `x86-` row to the existing builder catalog so the
  generic local publisher derives `x86-*` versioned tags and `x86-latest`.
- Publish a non-replaceable `x86-alpine-3.24.1-r1` builder with SBOM and
  provenance, verify it anonymously, and adopt its immutable digest.
- Document the available builder and its platform translation without yet
  claiming a distributed `x86` utility.

Out of scope:

- Adding a recipe-catalog row, recipe, artifact directory, checksum, or trust
  record; those belong to the ordered per-artifact plans.
- Preinstalling dependencies for utilities outside the current six-tool set or
  changing a tool's established feature profile merely to share a package.
- Supporting i386, i486, i586, x32, DOS/Windows executables, or a CPU without
  CMOV and SSE2.
- Refactoring the architecture-owned builder validation or changing the generic
  builder-catalog consumers established by the prerequisite plan.

## Design

Use these exact translations:

| Concern | Value |
| --- | --- |
| Repository and Alpine identifier | `x86` |
| CPU baseline | i686-compatible with CMOV and SSE2 |
| Docker/Buildx platform | `linux/386` |
| OCI architecture | `386` |
| ELF contract | ELF32, little-endian, machine `Intel 80386`, `ET_EXEC` |
| binfmt installation target | `386` (`qemu-i386`) |
| Builder tags | `x86-alpine-3.24.1-r1`, `x86-latest` |

Reuse the architecture-owned builder layout. `environment.lock` pins the
Alpine `linux/386` child manifest, the existing binfmt helper digest, the
non-replaceable tag, and finally the published builder digest. Reconfirm the
Alpine child descriptor during execution rather than trusting the value copied
into this plan. `packages.lock` records exact direct packages resolved from
that base. Derive the package union from the current AArch64 and ARMv7 builders
and the six live recipe implementations: the static C/C++ toolchain, autotools,
Flex, Bison, Linux/RPC headers, libtool, pkg-config, tar and file utilities,
and the exact static development archives used by GDB, lsof, socat, strace,
and tcpdump. Retain a direct package only when a named recipe command, archive,
or candidate probe consumes it. Ordinary recipes must not run `apk add` or
resolve a replacement package set.

The candidate script must validate the package lock in one pass and probe all
shared recipe prerequisites before publication. Require the GDB archive set
(`libexpat.a`, `libgmp.a`, `libmpfr.a`, `libncursesw.a`, `liblzma.a`,
`libz.a`, and `libzstd.a`), lsof's no-Kerberos libtirpc static interface, and
the compiler/libc/pthread archives used by the remaining tools. Compile both C
and C++ static executables with the explicit i686/SSE2 baseline. Do not compile
the utilities themselves in the builder plan; their tool-owned recipes retain
source, link, and functional validation.

Follow the existing Buildx-only candidate path. Check Docker and Buildx before
pulling images, registering emulation, creating output, or compiling. First try
the pinned `linux/386` Alpine image directly; an x86-64 Linux kernel may execute
it through native 32-bit compatibility. Only if that fails, install `386` from
the pinned binfmt image and prove the image executes before continuing.

Do not use `uname -m` as the x86 identity invariant: a 32-bit container shares
the host kernel and may report differently between native compatibility and
QEMU paths. Validate actual target state instead: require `apk --print-arch` to
report `x86`, inspect `/bin/sh` and compiled probes as ELF32 little-endian
`Intel 80386`, and inspect the loaded and published image as OCI `386`. Compile
with `-march=i686 -msse2 -mfpmath=sse` so CMOV and SSE2 are explicit rather than
host-derived, reject an interpreter and all `DT_NEEDED` entries, and execute
every probe through `linux/386`.

Add only the bounded x86 row to `builders/catalog.tsv`; do not change the
generic publisher. The publisher derives the builder directory, `linux/386`
platform, `x86-` versioned prefix, and `x86-latest` from that row, then retains
its non-replacement, candidate validation, Buildx, SBOM, provenance, platform
inspection, and digest-reporting behavior. Publish first, inspect the result,
then commit `BUILDER_IMAGE`; never substitute a mutable tag or another
architecture's builder.

## Affected Components

- `builders/x86/{Dockerfile,packages.lock,environment.lock,build.sh}`: own and
  validate the pinned 32-bit x86 build environment.
- `builders/catalog.tsv`: register the bounded internal identifier, OCI
  platform, and public builder-tag prefix.
- `doc/architecture/build/BUILD_ENVIRONMENTS.md`: record the builder identity,
  CPU baseline, and `linux/386` translation while distinguishing builder
  availability from recipe support.
- `README.md`: list the published x86 builder and maintainer publication
  command without adding a ready-to-run x86 row.

## Implementation Sequence

1. Start from a clean worktree. Reconfirm the Alpine 3.24.1 `linux/386` child
   digest and derive the minimal six-tool package union from the live recipes
   and existing architecture builders against that exact base.
2. Add the four `builders/x86/` files under the `x86-alpine-3.24.1-r1` tag with
   `BUILDER_IMAGE` intentionally absent. Add the single fixed x86 row to the
   builder catalog and prove the generic consumers derive the expected mapping.
3. Run the local candidate once, retaining BuildKit cache and diagnostic output
   for late validation corrections. Require the complete package, command,
   static-archive, pkg-config, exact compiler-baseline, C/C++ static ELF,
   execution, OCI-platform, and source-label checks to pass together.
4. Run `./builders/publish.sh x86`. Require the versioned tag to be unused,
   inspect the reported digest and both tags anonymously, and verify the
   platform, package inventory, labels, SBOM, provenance, and probe execution.
5. Add only that verified digest as `BUILDER_IMAGE`, update the two owning
   documents, rerun focused and repository validation, then commit and push the
   complete locked builder foundation.

## Validation

- Run `bash -n builders/x86/build.sh builders/publish.sh` and
  `git diff --check`.
- Run `./builders/x86/build.sh`; require the exact package lock, every command
  and static archive named by the six current recipe profiles, the exact
  libtirpc pkg-config result, Alpine `x86` identity, OCI `386` identity, the
  literal `-march=i686 -msse2 -mfpmath=sse` baseline, and executable C and C++
  static probes to pass.
- For each probe, require ELF32, little-endian data, machine `Intel 80386`,
  `ET_EXEC`, no requested interpreter, no `DT_NEEDED`, and successful
  `linux/386` execution.
- Run `./builders/publish.sh x86` exactly once for the new r1 tag. Inspect the
  reported digest and versioned/floating tags anonymously and confirm one
  `linux/386` manifest plus the expected labels, SBOM, and provenance.
- Run `./validate.sh` and confirm `./build.sh list`, `recipes/catalog.tsv`,
  `artifacts/SHA256SUMS`, and every distributed artifact remain unchanged.

## Success Criteria

- `builders/x86/environment.lock` names one publicly pullable, immutable
  `linux/386` builder whose base and direct package inputs are exact and
  sufficient for all six planned x86 recipes without package resolution.
- The candidate and published image prove the documented Alpine x86 baseline
  with executable static ELF32 probes and no mutable fallback.
- `./builders/publish.sh x86` is the single bounded maintainer publication
  command for the builder.
- The builder catalog recognizes x86, but the recipe catalog and distribution
  do not yet claim an x86 utility; activation occurs only in the ordered
  per-tool plans.
